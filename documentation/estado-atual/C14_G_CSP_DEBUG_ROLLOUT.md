# C14-G — CSP do Pages e superfícies de diagnóstico

Status em 29/09/2026: implementação local em andamento; não publicada. Chat-Origin: Trofia-Principal.

## Escopo e limite

O escopo aprovado é acrescentar uma política de segurança de conteúdo ao HTML publicado no GitHub Pages e retirar helpers globais exclusivamente diagnósticos do ambiente de produção. As pontes UMD/ESM, backup, Auth, Firestore, IA e reconhecimento por foto continuam necessárias ao aplicativo e não podem ser removidas por associação com a palavra `window`.

A CSP via `<meta http-equiv>` é aplicada pelo navegador ao documento a partir do ponto em que aparece. Por isso ela foi colocada antes do primeiro script do `index.html`. A hospedagem estática não fornece neste passo um cabeçalho CSP ou modo report-only; `frame-ancestors`, `report-uri` e `Content-Security-Policy-Report-Only` não podem ser obtidos por meta. Esses controles dependem de suporte futuro do host a cabeçalhos HTTP. Referências: [CSP do MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP), [reCAPTCHA e CSP do Google](https://developers.google.com/recaptcha/docs/faq).

## Inventário inicial

- `index.html` não tinha CSP. Contém dois blocos de JavaScript inline executáveis e um bloco de CSS inline; o script `type=module` externo não contém corpo. Os blocos executáveis receberam hashes SHA-256 exatos, sem `script-src 'unsafe-inline'` nem `'unsafe-eval'`. O verificador de build recusa qualquer edição desses blocos sem atualização da política e normaliza CRLF para LF como o parser HTML do navegador antes de calcular o hash.
- O bootstrap usa atributos `style` criados por JavaScript e componentes React também aplicam estilos inline. A política limita o CSS de elemento com hash, mas mantém `style-src-attr 'unsafe-inline'` por compatibilidade. Isto é uma exceção CSS, não uma autorização a scripts inline arbitrários.
- O App Check web carrega reCAPTCHA Enterprise de `www.google.com`/`www.gstatic.com` e troca o token com Firebase. A política lista somente as origens necessárias de reCAPTCHA, Firebase Auth/Firestore/App Check/Installations, Worker de IA, callable de exclusão e Open Food Facts. A [orientação oficial de reCAPTCHA](https://developers.google.com/recaptcha/docs/faq) inclui `script-src`, `frame-src` e `connect-src` específicos.
- `firebase-storage.js` publica `debugNutritionStorage`, que pode retornar valores de dados e UID, e `src/firebase/firebase-storage.js` publica `debugNutritionStorage` e `debugFirestoreReadMetrics`. Esses helpers não são fluxos de produto. Ficaram disponíveis apenas em `localhost`/`127.0.0.1` para diagnósticos locais; as demais pontes de produção foram mantidas. Os smokes locais que usam métricas continuam no host local.
- O `REPORT_SERVER_URL` é opcional e não está configurado no Pages atual. Um futuro servidor de relatórios exigirá revisão explícita de `connect-src`; não se abriu `https:` genericamente para acomodar um destino ainda não aprovado.

## Gates antes do PR e da publicação

1. Testes de contrato devem comprovar hashes de todo script/style inline, posição da meta, ausência de permissões amplas de script e ausência dos helpers de diagnóstico no host do Pages.
2. `npm run build:vite` deve verificar a CSP no `dist/index.html` depois da transformação do Vite, além da allowlist de artefatos.
3. Validar bootstrap/login, leitura de perfil, App Check/reCAPTCHA, Firestore, IA texto/foto, backup, idioma PT/EN/ES e build Android/WebView sem aceitar violações CSP ou loading permanente. O smoke autenticado e o CI pesado esperam o lease compartilhado da C14-F2 liberar.
4. O deploy do Pages e qualquer teste físico são posteriores ao PR draft e seus gates. Não publicar uma CSP que bloqueie algum fluxo legítimo; preservar rollback por revisão anterior do Pages.
